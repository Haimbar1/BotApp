## What this system is

The chatbot management piece of the "עסק חכם" (SmartEsek) product family — lets a business define one or more AI chat **agents** (bot personas with a system prompt, likely per-business or per-purpose), have them handle conversations coming in over WhatsApp/web/Facebook, and view/manage that chat history. Branded "SmartEsek" / "עסק חכם" at `app.smartesek.com`.

Part of a 3-piece ecosystem Haim is building toward treating as one product:
- **WhastAppSystem-** (`whatsapp.smartesek.com`) — bulk WhatsApp campaign sending + unified inbox.
- **CRM** (`crm.smartesek.com`) — lead management.
- **BotApp** (this repo, `app.smartesek.com`) — bot/agent configuration and chat handling.

Existing integration points between this and the other two:
- WhastAppSystem-'s `/api/bot-prompt` proxies into this app's `/api/agents` (get/set an agent's `businessPrompt`) so the bot's prompt can be edited from within WhastAppSystem- without a second login.
- CRM's `/api/bot/sync` receives conversation history — likely originating from this app or from WhastAppSystem-, not yet confirmed which; check `/api/sync` in this repo's `server.ts` (line ~2276) for what it actually pushes and where.

## Deployment: Vercel, like the other projects (used to be Cloud Run)

`server.ts` exports `createApp()` (all /api routes); `api/index.ts` wraps it as one Vercel serverless function and `vercel.json` rewrites `/api/*` to it, exactly like the CRM. Pushing to `main` deploys frontend and backend together. The old Google Cloud Run service is no longer used. Locally (`npm run dev`) or in a container, `startServer()` runs the same app plus Vite/static files. Environment variables (set in Vercel): DATABASE_URL, SSO_SHARED_SECRET, GOOGLE_CLIENT_ID, GEMINI_API_KEY, BOTAPP_SERVICE_KEY, META_APP_ID, META_APP_SECRET, EVOLUTION_API_URL, EVOLUTION_GLOBAL_KEY, optionally ALLOWED_EMAILS / PORTAL_URL.

## The help assistant ("העוזר")

A floating "?" for every signed-in user (`src/components/HelpWidget.tsx` — the same self-contained file in WhastAppSystem, TaskSystem and the portal; keep the copies in sync). It explains how to use all the SmartEsek systems and can point at the real buttons ("👆 הראה לי על המסך"). The brain is the CRM (`crm/server/helpBot.ts`; its guide `crm/server/helpKnowledge.ts` has a BotApp section — update it when a screen here changes). `/api/help/ask`, `/suggestions`, `/images/:id` in `server.ts` (`callHelp`) forward to the CRM's `/api/help/*` with `module: 'botapp'` and a 2-minute `x-insights-token` (SSO_SHARED_SECRET, the session's portal business), passing the streamed answer through.

## The CRM reads the bot's conversations (`POST /api/crm/bot-chats`)

The bot's answers live in n8n's chat memory, and n8n doesn't always report them to WhastAppSystem, so the CRM's campaign conversations / "סיכום קמפיינים" missed them (Haim, 2026-10-21). The CRM asks here, server-to-server (`x-crm-token` signed with SSO_SHARED_SECRET, `typ: 'bot-chats'`, the portal business id), with `{ phones, phoneNumberIds }`: the bots on that business or answering on its WhatsApp number (agents without a business are **not** included — other businesses' are among them), read through `fetchLiveChats` (the same n8n fetch `/api/chats` uses), only those phones, only messages with a real time, as readable text (`readableChatText`: the bot's JSON → reply + "• option" lines). Ids are a hash of the message (n8n's records may have none).

## The bot answering here instead of n8n ("🤖 הבוט החכם" — botEngine.ts, botStore.ts)

Haim, 2026-10-23: move the bot from n8n into this app, step by step, so it talks directly to the other systems and "knows everything". **Step 1 = the website widget** (tested on האופטיקה הטובה); next WhatsApp (point the webhook here instead of n8n — work out which bot from the payload's number ourselves, decode voice notes, WhatsApp lists instead of JSON — Haim has n8n's formatter code), then Facebook comments and Messenger.
- **Per agent, its own tables** (not on the agent document — the screen saves the whole agent list from the browser and would overwrite what the bot wrote): `botapp_bot_brain` (on/off for the web, Q&A, booking hours per weekday, voice notes), `botapp_bot_lessons`, `botapp_bot_notes`, `botapp_conversations` (messages appended in place). Without DATABASE_URL: `data/bot-store.json`.
- **A turn** (`runBotTurn`): the prompt n8n last got (`n8nSync.payload.Prompt`, else `businessPrompt`) with the portal's frames, + the Q&A + active lessons + the customer from the CRM (`POST {CRM_URL}/api/bot/tools`, `x-bot-token`, SSO_SHARED_SECRET, `typ: 'bot-tools'`, the agent's portal business — card, purchases / order status, upcoming exams, the campaigns they got with their text), then Gemini (`geminiFor` the business; gemini-3.5-flash with fallbacks) with tools: `link_customer_phone`, `get_available_slots` (booking hours minus the calendar's busy times), `book_appointment` / `reschedule_appointment` / `cancel_appointment`, `note_for_staff` (handoff = amber, bug = red — also a note on the CRM lead) and `learn_from_correction` (active at once, shown as a blue note, can be turned off). Answer `{ reply, options, images }`. Style (Haim, 2026-10-23): the first reply of the day opens with a greeting by the time of day / Shabbat / a Hebrew-calendar holiday (`@hebcal/core`) or a day in `SPECIAL_DAYS` (election day) + the customer's first name (WhatsApp profile or CRM — whichever looks like a real name; a known customer is greeted as one); emojis, `*bold*` for the important bits, `•` lists (`tidyText` fixes markdown the model writes, and puts the stars at a word's edge — `מקבל*x*` → `מקבל *x*`, `ב*x*` → `*בx*` — or WhatsApp doesn't bold; the web widget shows `*bold*` bold); options on almost every reply, and slot offers always add "📅 שבוע הבא" / "🕐 מועד אחר".
- **Web**: the widget asks `/api/public/bot-engine?bot_id=` and, when on, posts to `/api/public/chat` instead of n8n (same payload; the answer's `phone` / `name` are kept in the browser). On the web the phone isn't verified (anyone can type a number), so the staff's notes from the CRM are not given to the bot there. Every web exchange is also reported to WhastAppSystem's `/api/webhook` as `web_bot_message` (its Messages + handoff / unhappy alerts, as n8n did; another business than the optics with an `x-wa-session` JWT). Conversations show in "לוג שיחות" (`/api/bot-conversations`, merged with n8n's; notes as colored lines, ids `staffnote-<kind>_…`) and reach the CRM through `/api/crm/bot-chats`.
- **WhatsApp** (step 2, Haim 2026-10-23; `whatsapp.ts`, `POST/GET /api/webhooks/whatsapp`): the business's WABA is pointed here (the tab's "💬 וואטסאפ" card, step 1 → `/api/whatsapp/subscribe-webhook` with `https://app.smartesek.com/api/webhooks/whatsapp`, verify token `smartesek-botapp` / `WHATSAPP_VERIFY_TOKEN`). The bot is found by the payload's number (`agentForNumber` — the same lookup `/api/whatsapp/n8n-credentials` uses). Its switch off (`brain.nativeWhatsapp`) → the payload goes on to n8n untouched (`N8N_WHATSAPP_URL`, default `…/webhook/whatsappopt`), so routing changes nothing by itself. On → a voice note is transcribed (Gemini, the media downloaded with the agent's token) and written into the payload as `text.body = "🎤 …"`, the payload is copied to WhastAppSystem's `/api/webhook` (what n8n's "forward a copy" did — inbox, blacklist, triage; every screen then shows the transcript as the message), the message is marked read with "typing…" (`keepTyping` renews it every 20s until the answer is sent — Meta drops it after 25s and a voice note takes longer), the bot answers (`channel: "whatsapp"`, the phone is verified, session `wa_<972…>`), the answer goes out through Meta (`answerToWhatsApp` — images, then text or an interactive list for the options; the shapes of n8n's formatter) and each piece is reported as a `bot_reply` with `phoneNumberId` + `decided: true` (handoff alert only with `handoff: true`). Each incoming message is answered once (`botapp_wa_seen` — Meta re-delivers). No signature check (n8n had none either); Meta only lets the business answer someone who wrote in the last 24h. `META_GRAPH_URL` points Meta at a mock in local tests.
- **Confirm first** (Haim, 2026-10-23 — it booked a day the customer only mentioned, and handed off a voice note it misheard as "it hurts"): book / move / cancel and, on a voice note, `note_for_staff` / `learn_from_correction` are refused by the tool (`needsConfirmation`) unless the bot's previous message asked to confirm that exact action — the bot message stores it as `pending` (`book|<start>`, `move|<exam>|<start>`, `cancel|<exam>`, `voice`). The transcription prompt marks unclear words `[לא ברור]` instead of guessing.
- **No handoff on a thank-you** (Haim, 2026-10-23): `note_for_staff` handoff is refused when the customer's message is only thanks / goodbye / ok (`JUST_CLOSING`), and after a voice-note question only a "yes" (`SAID_YES`) lets the note through. `parseBotAnswer` also survives the model leaving out `{"reply":"` or typing line breaks inside the JSON. Before, the JSON's tail (`","options":[…]}`) went to the customer.
- **The screen** (`src/components/NativeBotPanel.tsx`): on/off, notes for the staff ("טופל"), Q&A (filled by the AI from the prompt the first time it opens — `/api/bot-brain/autofill`), lessons, booking hours, a test chat (`/api/bot-brain/test-chat`: reads the CRM, books / writes nothing, a correction there is the owner teaching) and the same knowledge as a voice-bot prompt (`/api/bot-brain/voice-prompt`). Explained to users in the CRM's `helpKnowledge.ts`.

## Storage: Postgres (database `botapp`), see storage.ts

Settings, agents, chats and login sessions are documents in table `botapp_store` (one row each, with a `tenant_id` column). Reads are synchronous from memory; every request first syncs changed documents from the database (`syncStorage`) and, on Vercel, its response is held until the request's writes are stored (`flushStorage`), so several serverless instances stay consistent. Table `botapp_phone_bot_map` (phone_number_id → bot_id, agent_id, display_phone, waba_id) is derived from the agents' `whatsappConfig` and rewritten on every agent save (and at startup); `/api/whatsapp/n8n-credentials?phoneNumberId=…` (or `displayPhoneNumber=`) looks the bot up there first and returns `botId` + `agentId` with the token. Without DATABASE_URL it falls back to the JSON files in `data/` (local dev only; data is then not durable). Login: Google or the portal's SSO only; sessions are real tokens stored in the database. The old passcode ("bypass") login was removed; the WhatsApp system's prompt proxy signs in through `/api/auth/service-login` with BOTAPP_SERVICE_KEY.

## Auth

Google OAuth (`/api/auth/google`) and the portal's SSO (`/api/auth/sso`); only session tokens issued by the server at login are accepted (`requireAuth`). There is no passcode login any more (`/api/auth/bypass-login` answers 410). `ALLOWED_EMAILS` (comma-separated) and `GOOGLE_CLIENT_ID` env vars can override the stored settings.

## WhatsApp connection: Evolution API, not Meta's official Cloud API

This repo talks to WhatsApp through a **self-hosted Evolution API instance** (`/api/evolution/*` routes — create/recreate instance, QR-code connect, connection state, logout, incoming-webhook receiver at `/api/webhooks/evolution`), an open-source, unofficial WhatsApp bridge — **not** the same Meta Cloud API integration WhastAppSystem- uses. Default API URL in code: `http://72.61.185.147:60486` (same host IP, different port, as the Postgres server configured for the CRM project — Haim appears to run multiple self-hosted services on one VPS at that IP). Don't assume WhastAppSystem-'s Meta-API patterns (template messages, webhook payload shapes, etc.) carry over here — this is a genuinely different WhatsApp integration mechanism with its own quirks.

## Known cross-project issue (from earlier WhastAppSystem- work)

While building WhastAppSystem-'s bot-prompt-editing proxy, `/api/auth/bypass-login` returned a 404 in production (via the `app.smartesek.com` custom domain) even though `/api/agents` worked fine — suspected to be an incomplete Vercel-domain-to-Cloud-Run routing/rewrite configuration (a path missing from whatever proxy config sits in front of the actual Cloud Run service), not a bug in this repo's own code. A workaround (`BOTAPP_SESSION_TOKEN`, copying a live session token manually) was used instead of a real fix. If revisiting this, the fix likely belongs in whatever's proxying the custom domain to Cloud Run, not in `server.ts` itself — but this wasn't independently re-verified in this session.
